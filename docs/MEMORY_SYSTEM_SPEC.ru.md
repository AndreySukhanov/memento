# Система памяти агента - спецификация для внедрения

Описание системы памяти Claude Code агента для переноса в другой проект.

## Ключевой принцип

Никаких векторных баз, эмбеддингов и специальных API. Вся память - обычные markdown-файлы,
которые агент читает и пишет стандартными файловыми инструментами (Write, Edit, Read, Glob, Grep).
Система держится на двух вещах:
1. Жесткий формат файлов (конвенции ниже).
2. Индекс памяти автоматически подгружается в контекст каждой новой сессии.

## Три уровня памяти

### Уровень 1 - CLAUDE.md проекта (устав)

- Лежит в корне рабочего репозитория, коммитится в git.
- Загружается в контекст каждой сессии автоматически.
- Содержит только стабильные правила и указатели: правила безопасности, навигацию по документации,
  операционные команды. НЕ факты и НЕ логи.
- Меняется редко. Если что-то меняется каждую сессию - этому не место в уставе.

### Уровень 2 - Auto-memory (факты между сессиями)

Живет ВНЕ репозитория, в отдельной директории, привязанной к проекту:

```
<home>/.claude/projects/<project-slug>/memory/
|- MEMORY.md              <- индекс, грузится в контекст каждую сессию
|- feedback_style.md      <- отдельные файлы-факты
|- project_xxx.md
|- reference_yyy.md
```

**Именование файлов**: `<тип>_<slug>.md` - тип памяти вынесен в префикс имени файла
(`feedback_sql_comment_style.md`, `project_knowledge_graph.md`, `reference_dbgate.md`).
По имени файла сразу видно, что это за память, без открытия.

**Один файл = один факт.** Формат файла:

```markdown
---
name: short-kebab-case-slug
description: однострочное резюме - по нему решается релевантность при recall
metadata:
  type: user | feedback | project | reference
---

Сам факт.

**Why:** почему это правило появилось (для type: feedback/project).
**How to apply:** как применять на практике.

Связи: [[name-другой-памяти]]
```

Четыре типа памяти:
- `user` - кто пользователь: роль, экспертиза, предпочтения.
- `feedback` - корректировки от пользователя ("никогда не делай X", "всегда делай Y"),
  обязательно с объяснением почему.
- `project` - активные задачи, цели, ограничения, которые не выводятся из кода/git.
- `reference` - указатели на внешнее: URL, дашборды, тикеты, инструкции доступа.

**MEMORY.md - индекс.** По одной строке на память:
`- [Заголовок](file.md) - крючок-резюме`.
Только индекс грузится в контекст автоматически; тела файлов агент читает по требованию,
когда description показывает релевантность. Это и есть механизм recall: дешево по токенам,
индекс работает как оглавление.

Как устроен индекс на практике:
- Строки сгруппированы тематическими секциями с заголовками
  (Scope, Активные планы, Завершенные, Предпочтения пользователя, Карта репозитория).
- Завершенные задачи не удаляются из индекса, а сворачиваются в одну строку
  с итогом в секции "Завершенные (sealed)".
- Исключение из правила "только ссылки": небольшое число ЗАКРЕПЛЕННЫХ критических
  блоков (правила безопасности, окружения, жесткие запреты) живет прямо в индексе -
  они обязаны быть в контексте каждой сессии целиком, ссылки недостаточно.
  Таких блоков должно быть мало, и это должны быть именно правила, а не факты.

**Правила гигиены (критично для качества):**
1. Перед записью проверить, нет ли файла, который уже покрывает факт.
   Обновлять существующий, а не плодить дубликаты.
2. Ошибочную память удалять, не оставлять "на всякий случай".
3. Не сохранять то, что уже записано в репозитории (структура кода, история фиксов,
   git history) - память хранит только невыводимое.
4. Относительные даты ("вчера", "на прошлой неделе") конвертировать в абсолютные при записи.
5. Ссылки [[name]] между памятями - активно; несуществующий линк не ошибка,
   а пометка "стоит написать".
6. Индекс держать коротким: одна строка на память, содержимое - только в файлах-фактах
   (исключение - закрепленные критические блоки, см. выше).
7. Память отражает то, что было верно НА МОМЕНТ записи. Если воспоминание называет
   файл, флаг или команду - перед тем как рекомендовать/использовать, проверить,
   что это все еще существует.
8. Инструментарий может добавлять в frontmatter служебные поля (id сессии-источника
   и т.п.) - это допустимо, обязательный минимум: name, description, metadata.type.

### Уровень 3 - Папка задачи (per-task память)

Порог создания: задача многосессионная, со стейкхолдерами и артефактами.
Для разовых задач папку не создавать.

Структура (5 файлов + артефакты):

```
<workspace>/<TASK_NAME>/
|- CLAUDE.md       <- константный контекст задачи: цель, ID тикета, scope, ограничения
|- MEMORY.md       <- лог фактов: цитаты стейкхолдеров, кейсы, находки (только append)
|- TASKS.md        <- чеклист с фазами и статусами
|- DECISIONS.md    <- журнал решений: D1, D2... с датой, кто решил, почему
|- Description.txt <- карточка задачи: исходная постановка, сценарий, Definition of Done
|- исходники/      <- сырые артефакты (дампы, CSV, скрипты, PDF, переписка)
```

Разделение ролей файлов принципиально:
- CLAUDE.md - "устав" задачи, current-state-only, редко меняется. Явно фиксирует
  scope ("в scope" / "НЕ в scope") и рабочее окружение.
- MEMORY.md - "лог", только пополняется (append-only). Канонические секции:
  "Факты от стейкхолдеров" (цитаты с датами и указанием источника),
  "Дебаг-фактура" (кейсы: дата, источник, вывод), "Технические находки",
  "Открытые вопросы".
- DECISIONS.md - нумерованные решения. Формат блока: `## D<N>. <Заголовок>`,
  внутри: **Решение** / **Почему** (с цитатами и ссылкой на исходник).
  Пересмотр оформляется как `## D<N>.M. [Пересмотр D<N>, <дата>]` - старое решение
  НЕ удаляется, поверх пишется новое с пометкой, какие артефакты устарели.
  Решения не удаляются никогда; на них ссылаются короткими метками ("см. D7").
- TASKS.md - живой чеклист, разбит на фазы
  (Phase 0 исследование -> Phase 1 согласование -> Phase 2 реализация -> ...).
- Description.txt - человекочитаемая карточка (постановка, сценарий, DoD),
  синхронизирована с тикет-трекером.

**Инициализация папки - отдельной командой из шаблонов.** Папка не собирается руками:
есть команда (у нас `/ntask`), которая по 7-шаговому алгоритму
(проверить папку -> классифицировать материалы -> извлечь факты -> создать/обновить
5 файлов из шаблонов -> обновить корневой индекс -> обновить auto-memory ->
отчитаться) наполняет структуру из сырых материалов (переписки, скриншоты, карточка
тикета). Шаблоны 5 файлов лежат в одном месте (`<home>/.claude/templates/<тип-задачи>/`)
и содержат плейсхолдеры + подсказки по заполнению каждой секции.

**Корневой индекс рабочего пространства** - обязательный элемент уровня 3.
В корне workspace лежит свой `MEMORY.md` (в Memento - `INDEX.md`),
общий для всех задач:
- команда и роли стейкхолдеров (кто за что отвечает, кому какие артефакты передавать);
- доменные знания, общие для всех задач (архитектура системы, конвенции);
- таблица активных задач со статусами + хронология;
- исправления ошибочных фактов делаются ЛИНЗОЙ-ПОМЕТКОЙ ("до <даты> роль X была
  атрибутирована неверно, старые записи читать через эту призму"), а не тихой
  правкой истории. Линза пишется один раз наверху файла и исправляет чтение
  десятков старых записей, не трогая их; история остается аудируемой.
  Прямая правка допустима только для опечаток и одиночных строк;
- статусные глифы: секции и строки индексов/задач помечаются односимвольным
  статусом (🟢 активная / ✅ завершена / 🗂️ legacy и т.п., легенда в шапке файла).
  Это триаж, не украшение: длинный файл сканируется за один проход, а
  протухший статус ("горит" трехмесячной давности) сам по себе сигнал.

**Синк-ритуал в конце сессии:** обновить TASKS.md / MEMORY.md / DECISIONS.md по итогам
сессии, статус задачи отразить одной строкой в корневом индексе workspace и в
глобальном индексе auto-memory (уровень 2).

Референсная реализация опубликована как плагин (EN-обобщение этой системы):
https://github.com/AndreySukhanov/memento - версия 1.2.1, восемь правил
(порог, роли файлов, решения без удаления, синк-ритуал + проактивное предложение
синка по дрейф-триггерам, sealing + дедуп при дописывании, линзы-коррекции,
статусные глифы, атомарная auto-memory). Отличия имен от нашей локали:
Description.txt -> BRIEF.md, корневой индекс -> INDEX.md. Плагин покрывает
уровни 2-3 и автозапоминание; уровень 1 (устав проекта) и Stop-хук бэкапа
в плагин не входят - их внедрять по этой спеке отдельно.

## Автозапоминание - когда агент пишет память сам

Память пишется агентом ПО ТРИГГЕРАМ, без просьбы пользователя. Просьба "запомни" -
частный случай, а не основной канал.

### Триггеры записи в auto-memory (уровень 2)

- Пользователь дал корректировку или подтвердил подход ("никогда не делай X",
  "вот так правильно") -> файл `feedback_*` с объяснением почему. Записывать
  и корректировки, и подтвержденные приемы.
- Выяснился устойчивый факт о пользователе (роль, предпочтения) -> `user`.
- Появилась/изменилась многосессионная задача или ограничение, не выводимое
  из кода -> `project_*` (создать или обновить статус).
- Найден внешний ресурс, который понадобится снова (URL, тикет, инструкция
  доступа, алгоритм с граблями) -> `reference_*`.
- Пользователь просит запомнить то, что и так выводимо из репозитория ->
  не записывать как есть, а спросить, что именно неочевидно, и записать это.

### Порог создания папки задачи (уровень 3)

Полная папка (5 файлов) создается, если выполнен ХОТЯ БЫ ОДИН критерий:
- задача займет больше 1 рабочего дня;
- замешано больше 2 стейкхолдеров с разными ролями;
- нужен артефакт для релиза (SQL-скрипт, спека, PR);
- больше 2 последовательных фаз (исследование -> согласование -> правки -> тест -> релиз).

Иначе (быстрая разовая задача) - только reference-файл в auto-memory. Папку
не создавать: 5 файлов на разовый вопрос - оверхед. Сомневаешься - спроси
пользователя: "папку заведем или только в reference зафиксируем?"

**Регистрация атомарна с созданием**: сразу после создания папки следующим
действием обновить корневой индекс workspace и auto-memory (project-файл +
строка в индексе). Иначе индекс дрейфует от реальности.

### Лакмус "куда писать факт" внутри папки задачи

"Если факт можно удалить через неделю без потери смысла - это MEMORY.md.
Если факт актуален до смены scope задачи - это CLAUDE.md."

### Синк-ритуал: точный порядок

Запускается в конце сессии, где были действия по задаче (правка, запрос
стейкхолдеру, новая фактура). Чисто справочные вопросы синка не требуют.
На мелком факте допустимо обновить только MEMORY.md папки.

Полная последовательность (обязательна при пересмотре решения):
1. MEMORY.md папки - новая запись с цитатой и датой (кто когда что сказал);
2. DECISIONS.md папки - новый блок D<N>.M (почему и что теперь делаем);
3. CLAUDE.md папки - переписать разделы под актуальный устав (без истории);
4. TASKS.md папки - пометить устаревшие чекбоксы, добавить новые;
5. project-файл в auto-memory - обновить статус с датой;
6. строка в индексе auto-memory - поправить хвост, если статус устарел.

При завершении задачи: строка в индексах переезжает из "Активные" в "Завершенные"
с финальным итогом и ссылкой на артефакт.

### Recall на практике

- Индекс auto-memory - в контексте каждой сессии автоматически.
- Тела файлов агент подтягивает сам, когда description совпадает с темой работы.
- Подтянутая память - фоновый контекст, не команда: она отражает момент записи,
  агент обязан перепроверить актуальность перед применением (правило гигиены 7).

## Сжатие памяти (sealing) - защита от разрастания

**Проблема.** MEMORY.md задачи append-only, растет каждую сессию и рано или поздно
перестает влезать в контекст, который должен был экономить. Файл памяти, слишком большой
для загрузки, - тот же провал, что и отсутствие памяти.

**Решение - "запечатывание" (seal), а не удаление:**

1. **Бюджет размера**: ~250 строк или ~12 KB. Пересекли - пора сжимать.
   До бюджета не сжимать: преждевременное сжатие теряет детали без выгоды.
2. **Свежая треть записей не трогается** - остается сырой (уровень L0).
3. **Старые две трети триажатся построчно:**
   - Все еще несущее (живое ограничение, незакрытый тред, факт, меняющий сегодняшние
     действия) - запечатать: переписать в одну сжатую фразу.
   - Шум (пройденные прогоны тестов, устаревшие цифры, бытовая переписка) - выбросить.
   - Обоснования решений - не сюда: их место в DECISIONS.md; если там нет - флаг,
     а не запечатывание.
4. **Выжившие** складываются в блок `## Sealed (before <дата>)` внизу файла,
   сгруппированные по периодам, по несколько строк на период.
5. **Уровни, не стирание**: свежее - сырье (L0); первый seal сворачивает сезон в абзац (L1);
   когда sealed-блоки сами копятся - старейшие сворачиваются в одну строку на квартал (L2).
   На любом уровне можно восстановить "что мы знали и когда".
6. **Лакмус**: "сжатое до одной фразы - задача все еще понятна через месяц?"
   Да - запечатать. Уже неважно - выбросить. Влияет на действия сегодня - оставить живым.
7. **Неприкосновенны**: CLAUDE.md (и так current-state-only) и DECISIONS.md
   (решения не удаляются). Сжимается только MEMORY.md.
8. **Никогда не выдумывать**: sealing только сжимает существующее; сомневаешься,
   нужна ли строка - оставь живой.

**Запуск**: вручную по запросу, либо автоматически внутри синк-ритуала конца сессии,
когда бюджет пересечен.

Статус в нашей практике: правило действует, но полный seal с блоком `## Sealed`
пока ни разу не понадобился - бюджет не пересекался. Реально применяемая часть:
завершенные задачи сворачиваются в одну строку в секции "Завершенные (sealed)"
глобального индекса.

**Отчет обязателен**: цифры before/after (строки и KB), сколько запечатано, сколько
выброшено, сколько оставлено живым. Если бюджет не пересечен - честно сказать
"еще маленький, сжимать нечего" и остановиться.

## Хук автобэкапа памяти

Память - файлы, которые агент сам же и редактирует, а значит может случайно затереть
или испортить факт. Страховка - автоматический снапшот после каждого ответа агента.

В `.claude/settings.local.json` проекта настраивается хук на событие Stop
(срабатывает при завершении каждого ответа):

```json
"hooks": {
  "Stop": [
    {
      "matcher": "",
      "hooks": [
        {
          "type": "command",
          "command": "powershell -NoProfile -ExecutionPolicy Bypass -File \"<project>\\.claude\\backup_memory.ps1\""
        }
      ]
    }
  ]
}
```

Скрипт бэкапа (`.claude/backup_memory.ps1`), обязательные свойства:
1. Копирует ТОЛЬКО файлы памяти, не весь проект: корневые *.md (CLAUDE.md, MEMORY.md,
   DECISIONS.md и т.п.) + папки знаний.
2. Складывает в `backups/backup_YYYY-MM-DD_HH-mm-ss/`.
3. Ротация: хранит последние 20 бэкапов, старые удаляет.
4. Никогда не падает: любая ошибка глотается в try/catch - хук не должен ломать
   завершение сессии.

Эффект: версионированность памяти без git, откат любого файла на 20 снапшотов назад.

## Инструменты

| Операция          | Инструмент              | Комментарий                                  |
|-------------------|-------------------------|----------------------------------------------|
| Запись памяти     | Write                   | новый файл-факт + строка в MEMORY.md         |
| Обновление        | Edit                    | точечная правка существующего файла          |
| Recall            | автозагрузка индекса + Read | тело файла читается по требованию        |
| Поиск по памяти   | Grep / Glob             | обычный текстовый поиск по директории        |
| Удаление          | rm через shell          | для ошибочных/устаревших фактов              |
| Бэкап             | Stop-хук + PowerShell   | автоснапшот с ротацией                       |

Больше ничего. Ни одного специализированного "memory tool" нет.

## Рецепт внедрения (по шагам)

1. Создать директорию памяти вне рабочего репозитория, привязанную к проекту.
2. Обеспечить автозагрузку MEMORY.md (индекса) в системный контекст агента при старте
   каждой сессии. Это единственная инфраструктурная часть, все остальное - конвенции.
3. Дать агенту в системный промпт правила: формат файла-факта, 4 типа, правила гигиены
   (дедуп, удаление, абсолютные даты, "не хранить выводимое") и ТРИГГЕРЫ автозаписи
   (раздел "Автозапоминание") - без триггеров система превращается в
   "запоминаю только по просьбе" и умирает.
4. Для многосессионных задач внедрить структуру папки задачи (CLAUDE.md / MEMORY.md /
   TASKS.md / DECISIONS.md / Description.txt / исходники) + шаблоны + команду
   инициализации + корневой индекс workspace + синк-ритуал конца сессии.
5. Внедрить sealing с бюджетом ~250 строк / ~12 KB для append-only логов.
6. Настроить Stop-хук с бэкап-скриптом и ротацией.

## Заимствованные концепты из других систем

Система не выдумана с нуля - ключевые идеи взяты из существующих memory-систем.
Агенту-внедренцу полезно знать источники, чтобы при развитии смотреть туда же.

### Из OpenClaw (open-source агент, экс-Clawdbot)

- **Local-first Markdown-память**: память агента = обычные файлы на диске, не БД.
  Человек может читать и править память в любом редакторе, diff виден в git.
- **Формат MEMORY.md / USER.md**: индекс + отдельные файлы, наш формат auto-memory
  близок к нему.
- **Portable skills**: навыки как переносимые папки с инструкциями, а не зашитый код.
- Важный вывод из нашего опыта: полностью заменить БД на Markdown нельзя в
  multi-tenant системах - там Markdown работает как СЛОЙ ПОВЕРХ хранилища
  (экспорт/импорт), не как замена.

### Из Honcho (Plastic Labs, память для AI-агентов)

Статус: ИЗУЧЕНО, НЕ ВНЕДРЕНО. Как сервис не используем (AGPL-3.0 для self-host +
требования локализации персональных данных). Концепты зафиксированы как направление
развития - при внедрении в другой сервис это опциональный "этап 2", не часть базовой
системы:

- **Peer representations**: о каждом участнике (пользователь или агент) строится
  представление-профиль, а не плоский список фактов.
- **Automatic conclusions** (deductive + inductive): система сама выводит обобщения
  из повторяющихся наблюдений. Пример: пользователь 5 раз просит короче -
  вывод "предпочитает сжатые ответы" появляется сам, без ручной записи.
  В нашей ручной системе это делает дисциплина агента; conclusions - направление
  автоматизации.
- **Multi-peer perspectives**: данные хранятся по парам (наблюдатель, наблюдаемый) -
  что X знает об Y отдельно от того, что Y знает о себе.
- **Hybrid search**: BM25 + векторный поиск по памяти (у нас пока только Grep,
  это кандидат на апгрейд при росте объема).

## Главный урок эксплуатации

Система живет не за счет инструментов, а за счет дисциплины:
- обновлять память при каждом новом факте от пользователя;
- сливать дубли, удалять ошибочное;
- держать индекс коротким (одна строка на память), чтобы он не съедал контекст;
- запечатывать логи по бюджету, а не по настроению;
- бэкапить автоматически, потому что агент правит собственную память.
